加后端：用什么、怎么加

结论先说：用 Supabase（免费、不用自己写服务器）。下面是三选一的对比、建表 SQL、以及前端只改哪四行。

一、后端只解决三件事

要做的事没有后端时有后端后
两台手机看同一个冰箱（家庭码生效）各自的 localStorage，互相看不见同一张表，谁加的都看得到
墨水屏读到手机加的东西只有同机同浏览器屏每 5 秒拉一次
采纳率（✓/✕）汇总只在本机，换个手机就没了所有人的按键汇总成一个数

菜谱、模型、网页都不需要后端 —— 那些放静态文件就行（见 架构页）。

二、三个候选，为什么选第一个

服务是什么免费额度适合谁
Supabase
推荐		 托管 Postgres + 自动生成 REST 接口 + 匿名登录 2 个项目、500 MB 数据库、实时推送免费 课程项目、要快、要英文文档、不想写服务端代码
Firebase（Firestore） Google 的文档数据库 1 GB 存储、每日读写配额 要做原生 App、以后想接推送
腾讯云开发 CloudBase
如果用户在内地		 微信生态原生，境内速度快 有免费额度，按月重置 最终要给妈妈那一代人在内地用 —— 访问速度和微信登录都更合适

为什么不是"自己写个服务器"：你要的是三张表和一个接口，写服务器等于给自己找运维。Supabase 把这三张表直接暴露成 REST，前端 fetch 就完事。

三、四步接上（大概半天）

  1. 去 supabase.com 注册（GitHub 账号一键登录），新建一个 project，区域选 Singapore。
  2. 进 SQL Editor，把下面这段粘进去执行 —— 三张表和权限一次建好。
  3. 进 Project Settings → API，复制 Project URL 和 anon public 两个值。
  4. 把这两个值填进 sync.js 顶部两行，前端再加一句 <script src="sync.js"> —— 后端就通了，其余代码不用动。
-- 一个家庭 = 一个家庭码；物品挂在家庭下
create table households (
  code        text primary key,           -- 6 位家庭码，如 DTSU6U
  created_at  timestamptz default now()
);

create table items (
  id          text primary key,
  household   text references households(code) on delete cascade,
  cat         text not null,              -- tofu / greens / egg …
  name        text,
  tag         text,
  qty         int default 1,
  unit        text,
  life        int,                        -- 保质天数
  days_left   int,
  added_at    date,
  by          text,                       -- 谁放的
  updated_at  timestamptz default now()
);

create table logs (                        -- ✓/✕ 采纳记录
  id          bigserial primary key,
  household   text,
  action      text check (action in ('take','skip')),
  recipe_id   text,
  at          timestamptz default now()
);

-- 打开行级权限（Supabase 默认关，必须开）
alter table items  enable row level security;
alter table logs   enable row level security;

-- 课程演示用：谁拿到 anon key 谁都能读写这个家庭。
-- 真上线要换成 auth.uid() 绑定家庭，见文末。
create policy "demo read"  on items for select using (true);
create policy "demo write" on items for insert with check (true);
create policy "demo upd"   on items for update using (true);
create policy "demo del"   on items for delete using (true);
create policy "demo log"   on logs  for insert with check (true);
create policy "demo logr"  on logs  for select using (true);

这段 SQL 是"演示级"权限：拿到 anon key 的人都能读写。交作业够用，但不能上线 —— 上线要接 Supabase 的匿名登录，把策略改成 auth.uid() 属于哪个家庭。

四、前端要改的地方（已经写好了）

sync.js 已经放在仓库里，是个"关闭状态"的同步层：URL/KEY 为空时所有函数直接返回 disabled，App 完全不受影响。填上两个值以后，只要在四个地方换成它：

原来的换成在哪
FD.saveItems(list)SYNC.add(code, item)加一样东西 / 闸机确认
FD.consume() 之后SYNC.update(code, id, {qty})做饭扣减
页面加载 FD.items()await SYNC.pull(code)App / 墨水屏 / 圆片
FD.log()SYNC.log(code, "take", id)✓ / ✕ 按钮
 
// 一旦同步层启用，屏子和别的手机就这样跟着动
SYNC.watch(householdCode, rows => {
  items = rows;
  renderItems();          // 别的手机加的东西，5 秒内出现在这里
}, 5000);

用纯 fetch 调 Supabase 的 REST 接口，不装 SDK、不需要构建步骤 —— 和现在这个站一样是静态文件。

五、成本与风险

项数字
钱0 元（免费额度：2 个项目、500 MB、每月 5 GB 流量）
一个家庭的用量几十 KB —— 免费额度的 0.01%
时间建项目 + 建表 ≈ 20 分钟；前端接线 ≈ 2 小时；调试权限 ≈ 1 小时
风险anon key 是公开的（前端代码里谁都能看到）→ 演示级策略下别人可以改你的数据。课程项目无所谓，上线必须换策略

如果用户主要在内地：Supabase 的节点在国外，访问会慢（有时几秒）。那种情况改用 腾讯云开发 CloudBase，逻辑几乎一样（云数据库 + 匿名登录），但境内速度正常、还能一键接微信。

六、我的建议：什么时候加

不要在周一之前加。理由：现在这套东西是纯静态、零故障点，演示不会挂；加后端会引入"注册/密钥/权限/网络"四个新的失败点，而老师在台上最不想看到的就是"连不上"。

顺序应该是：周一交 PPT → 交完当天接 Supabase → 下一节课演示"两台手机同一个冰箱"。那时候"家庭码真正生效"才是一个能演的东西，而不是一句话。

如果你希望我现在就把接线做完（留空密钥、填上就生效），说一声 —— 大概要动四个函数，我会保持"没填密钥时和现在完全一样"。
