# 冰箱决策 · 配套硬件方案 v1

> 2026-11-03 · 给组里看的版本
> 前提：软件已经在跑（GitHub Pages + Supabase + 端侧 9 类模型 + 小票 OCR），
> 所以硬件**不重新发明识别，也不新增第二个数据库**。

---

## 0. 一句话

硬件不做智能，只做三件软件做不到的事：**看得见**（不用解锁手机）、**拍得准**（光学与构图固定）、**不用手**（做饭时不用碰屏幕）。
算力、模型、判断全部留在现有 Web + Supabase 里。

```
        门贴 Panel（门外侧，常显）──┐
                                    ├──→ Supabase ──→ 手机 PWA（已有页面）
        拍位 Station（台面俯拍）  ──┤      ↑
                                    │   device-ingest（设备只持 id+secret）
        灶台键 Puck（BLE 键盘）   ──┘      不持任何 Supabase key
```

三个端点，一块后台。**不是三套系统，是三个"手"**。

## 1. 先把三个需求翻译成硬件任务

| 用户时刻 | 软件现在已经有的 | 硬件唯一要补的 | 明确不做的 |
|---|---|---|---|
| 出门前瞥一眼冰箱 | `display.html` 已按 296×128 设计好三屏 | 一个**不用充电线、不用解锁**的常显面 | 不做第二块触摸屏、不做手机镜像 |
| 买菜回来录入 | `add.html?v=detect`（拍照/相册/小票/多选） | **固定距离+固定光**的拍位；一个能单手按的快门 | 不做"放进冰箱自动记录" |
| 做饭时看步骤 | `cook.html` + `cook-steps.js`（20 道菜的动作插画） | 一个**不用洗手**就能"下一步"的实体键 | 不做投影、不做透明屏、不做眼镜 |

判断依据只有一条：**这三件事里，哪一件是手机放在口袋里做不到的？**
- 常显 → 手机做不到（要解锁、要打开 App、会没电）。
- 固定光学 → 手机做得到，但要一个工位才稳定（手举着每次距离/角度都不同）。
- 免触 → 手机做得到，但要一块擦得干净的屏幕。

## 2. 组里提过的四个形态，逐个裁决

| 形态 | 它真正想解决 | 裁决 | 理由（可写进报告） |
|---|---|---|---|
| **眼镜**（衣领摄像头） | 两手拎着菜也能拍 | ❌ 组里已 pass | 投影晃动 + 续航 + 每人一套；更硬的一条：**冰箱是全家共用的**，只有戴的人被记录，妈妈不戴就整份库存失真 |
| **小投影仪**（投桌面） | 做饭时抬头就能看到步骤 | ❌ 不做 | 厨房环境光/油烟/手挡光/梯形校正，90% 工时花在"投正"；内容只是几行字，投出来还没有手机清楚。演示现场灯光也不可控 |
| **触屏板**（放厨房） | 一块专门的菜谱屏 | ❌ 不做 | 组员自己说的"跟手机功能一样"；而且**做饭时触屏是最差输入**（油手、水汽、戴手套） |
| **透明棱镜小电视**（holocubic，¥305） | 有未来感的显示 | 🟡 只做氛围件 | 5.7 cm 有效画面、分辨率低、要暗背景；能显示**一个图标**，显示不了菜谱步骤。可作为 Stretch 的展台摆件，不进主链路 |

**被否掉的不是"想法"，是"载体"。** 投影想要的"抬头就能看见"，用 **手机立在支架上 + 语音朗读 + 一个实体键** 就能拿到 90% 的效果，成本 1/20，而且在明亮的厨房里真的看得见。

## 3. 端一：门贴 Panel（提醒）

### 3.1 选型

| 件 | 型号 | 为什么是它 | 价格 |
|---|---|---|---|
| 屏 | Waveshare 2.9″ e-Paper Module (B) 296×128 三色 | 断电不丢画面、无背光、贴在门外侧不结露；分辨率正好等于 `display.html` 已设计的画布 | ≈¥135 / HK$150 |
| 主控 | Seeed XIAO ESP32S3 | 自带锂电充电管理、21×17.5 mm、深睡任意 GPIO 可唤醒（C3 只有 GPIO0–5 能唤醒，三个按键容易撞 strapping 脚） | ≈¥75 |
| 电 | 3.7V 1200mAh 软包（带保护板） | 目标 1–2 个月一充 | ≈¥25 |
| 交互 | 3× 12mm 轻触键 + 1× RGB LED | 采纳 / 不采纳 / 下一屏 + 即时反馈 | ≈¥10 |
| 结构 | 3D 打印壳 + 2× N35 10×3 磁铁 + 3M VHB | 冰箱门是钢板就吸，玻璃门就粘 | ≈¥15 |

单台 ≈ **¥260**，做两台（她家 + 妈妈家）≈ ¥520。

### 3.2 屏幕内容：直接沿用 `display.html`

| 屏 | 内容 | 为什么 |
|---|---|---|
| 1 · 决定 | 今晚吃这个（菜名 + 两个食材的图标 + 12 分钟） | 先给答案，再给数据 |
| 2 · 倒计时 | 先吃这个：虾 · **还剩 3 天**（红） | 只有红色一种强调色 |
| 3 · 全景 | 冰箱里 8 样 · 本周无忧 / 3 样要动 | 一眼看"整体危险度" |

一屏只放一件事。妈妈那台默认停在第 2 屏（她只需要知道"哪个快坏了"），她自己那台默认第 1 屏。

### 3.3 固件行为（唯一的复杂点，但很小）

```
唤醒（三种原因）
 ├ 30 分钟定时 → 画缓存里的第 i 帧（i = 当前半点 / 30 % 3）→ 立刻睡
 ├ 6 小时定时 → 先 HEAD 帧包 ETag；变了才下载 3 帧包（28 KB）→ 画 → 睡
 └ 按键唤醒   → 读引脚判断是哪个键 → POST 事件（失败就存 NVS，下次补发）
                → LED 闪一下 → 睡（不刷屏，见 3.5）
```

- 固件栈：Arduino + `GxEPD2` + `WiFiClientSecure` + `ArduinoJson`，约 250 行。
- **帧是 2bpp 缓冲（296×128 → 9472 B/帧），不是 BMP/PNG**：三色屏本来就要"黑位面 + 红位面"两张 1-bit 图，直接用 GxEPD2 的缓冲格式，固件里没有解码、没有取模、没有字库。
- Wi-Fi 只支持 2.4 GHz —— 路由要有 2.4G SSID（家里通常有）。
- 原型阶段 `setInsecure()` 跳过证书校验；写进报告的"已知简化"。

### 3.4 电源估算（写进报告的算法）

单次唤醒 ≈ Wi-Fi 联网 3 s × 110 mA（0.09 mAh）+ 刷屏 15 s × 20 mA（0.08 mAh）≈ **0.2 mAh**。
48 次/天 ≈ 10 mAh/天 → 1200 mAh 理论 4 个月，扣自放电和低温，**保守写 1–2 个月**。实测两周再定数字。

### 3.5 必须承认的物理限制：三色屏整屏刷新约 15 秒

所以"按一下翻页"这个交互在墨水屏上是错的。方案：

- 屏幕**按时间轮播**（30 分钟一次），不靠按键翻。
- 三个键只做**"采纳 / 不采纳 / 换一屏"**，按下只有 LED 即时反馈，画面等下一次轮播。
- 如果组里坚持要"按键即翻页"，就必须换**单色 2.9″**（0.3 s 局部刷新），代价是**失去红色**——而红色是这个产品唯一的紧急信号。二选一，别两边都要。

### 3.6 结构

105×62×14 mm，2 mm 壁厚，正面 1.5 mm 边框压住屏，背面两个磁铁仓 + 一条 VHB，右侧 USB-C 开孔（充电时不用拆）。
按钮做在**下沿**而不是正面：手上有水时用手背也能按。

## 4. 端二：拍位 Station（录入）

### 4.1 为什么"相机"用旧手机，而不是买模组

| | OV5640（ESP32-S3-CAM） | Camera 3 Wide（Pi） | 旧手机 |
|---|---|---|---|
| 水平视角 | 55° | 102° | ~70°（主摄） |
| 对焦 | **固定对焦**（20–40 cm 必糊） | PDAF 5 cm–∞ | 相位对焦 + 微距 |
| 30 cm 能拍多宽 | 31 cm（拍不满 52 cm 层板） | 74 cm | ~42 cm |
| 成本 | ¥120–150 | HK$450–520（Pi Zero 2 W + Cam3） | ¥0 |
| 现有页面能不能直接用 | 要写固件上传 | 要写 libcamera 服务 | **直接开 `add.html?v=detect`** |

结论：**课程项目里，手机是这套系统里最好的相机**。硬件的价值在"工位"，不在"模组"。
（模组路线不删除，放 Stretch，见 4.4。）

### 4.2 工位四件套（这才是要做的硬件）

| 件 | 做法 | 解决什么 |
|---|---|---|
| 磁吸悬臂 | 2020 铝型材 30 cm + 球头夹 + 3D 打印底座（内嵌磁铁） | 高度/角度每次都一样 → 对焦稳 |
| 补光灯 | 5V 4000K 灯条贴在横臂下沿 + 打印柔光罩（或硫酸纸） | 不用闪光灯直打 → 没有死白和硬阴影 |
| 标定垫 | A3 PVC 板 UV 打印：四角标 + 30 cm 刻度尺 + **小票槽**（5 mm 凹槽压住小票不卷） | 构图固定、拍满整屏、小票不跑 |
| 快门键 | 见第 5 节（同一个 puck，另一种键位） | 两手拎着菜也能拍 |

成本 ≈ **¥120**（灯条 25 + 垫子 30 + 铝型材与球头 40 + 耗材 25）。

### 4.3 "要从冰箱上拿下来拍" —— 直接满足

整根悬臂是**磁吸可拆**的：吸在冰箱侧面时是固定工位，取下来就是手持支架。
所以组员提的"拍摊开的物品和小票"，不需要第二个设备，只需要一个**能取下来的托架**。

### 4.4 如果评分硬性要求"自制相机"

同一根悬臂换 **Pi Zero 2 W + Camera Module 3 Wide**（HK$450–520），跑一个 80 行的 Python 服务：
`POST /capture` → 同一张 `capture_sessions` 表 → 手机端照样进"待确认"。
**接口不变，只换采集器**——这正是现在这套表结构（`capture_sessions.device_id` 已存在）的价值。
买之前先跑 2 天光学验证（20 种食材 × 3 个距离 × 2 种光照 + 5 张小票），别先买板子。

### 4.5 与现有页面怎么接

不改流程，只加一个入口：`add.html?v=detect` 已经有抓拍、缩图、超时看门狗。
新加的只有两行——全局 `keydown` 监听 Space → 触发同一个快门函数。

## 5. 端三：灶台键 Puck（做饭指引）

### 5.1 为什么不是一块屏

做饭这个场景的三个约束：**手是油的、眼睛在锅上、蒸汽**。
任何"看+点"的界面都在跟这三个约束打架。所以把交互从屏幕挪走：

**手机立在灶台边（屏幕常亮，显示当前步骤）+ 语音朗读 + 一个实体键"下一步"。**

### 5.2 硬件与固件

| 件 | 型号 | 说明 |
|---|---|---|
| 主控 | ESP32-C3 SuperMini | 只做 BLE HID 键盘，不联网、不连 Supabase |
| 电 | 500mAh 软包 + 充电板 | BLE 空闲即深睡，按一次醒一次 |
| 键 | 40 mm 硅胶大键（或锅盖把手式外接键） | 手背/手肘也能按 |
| 壳 | 3D 打印，底部防滑硅胶 | 放在灶台不滑 |

固件约 150 行（NimBLE HID keyboard），**一份固件两种键位表**：

| 模式 | 按键发送 | 用在哪 |
|---|---|---|
| A · 做饭 | →（下一步）/ ←（上一步）/ 空格（重复朗读） | `step.html` 做饭模式 |
| B · 拍摄 | 空格 | `add.html` 快门 |

同一个东西，两个场景。所以采购上是"两个 puck"（一个吸在冰箱侧给拍摄、一个放灶台），**开发上只有一份固件**。

### 5.3 配套的 Web 改动（这才是这个端的真正工作量）

现有 `cook.html` 把步骤放在 `<details>` 里一次列完——那是"看菜谱"，不是"做饭"。
新增**做饭模式**（可以新开 `step.html`，不改动现有页面）：

- 一次只显示一步：32 px 大字 + `cook-steps.js` 已有的 24×24 动作插画 + "第 2/5 步"
- 进入即用 `SpeechSynthesis` 朗读这一步（zh-CN），可重播
- `keydown` → ArrowRight/Left/Space 切步
- `navigator.wakeLock` 保持亮屏（iOS 16.4+ 支持）
- 屏上仍有大按钮兜底（蓝牙没连上也能用）

约 120 行，一个人三天。

### 5.4 风险

- **iOS 配对**：BLE HID 键盘在 iPhone 上能连，但连着键盘时输入框会隐藏软键盘。做饭模式没有输入框，问题不大；产品说明里写"只在做饭时连接"。
- 兜底：屏上大按钮永远在，蓝牙只是"更好用"，不是"必须能连"。

## 6. 数据链路与接口契约

### 6.1 现状（不动）

- 写库存只有两条路：`confirm_purchase`、`complete_meal`；其余一律不写 `qty`。
- 设备不持任何 Supabase key（`docs/进度_20261101.md` 已定的规矩）。
- `devices` 表已存在：`id / household_id / name / secret_hash / last_seen / firmware`。
- `capture_sessions.device_id` 已存在，所以"设备拍的照片"天然能落进现有确认流程。

### 6.2 新增一个 Edge Function：`device-ingest`

| 端点 | 方法 | 入 | 出 | 说明 |
|---|---|---|---|---|
| `/device-ingest/frame?d=<id>` | GET | header `x-device-secret` | 3 帧包（28 KB）+ ETag | 只读，顺手更新 `last_seen` |
| `/device-ingest/event` | POST | 同上 | 204 | `{type: take\|skip\|next, screen, meal_id?}` → 新表 `device_events` |
| `/device-ingest/capture` | POST | 同上 | `{session_id}` | JPEG → Storage → `capture_sessions(status='capturing')` + `capture_images` |

- 校验方式：`sha256(secret) == devices.secret_hash`，查不到 401。
- `device_events` 是这次唯一新增的表：`id / device_id / household_id / type / screen / meal_id / at`，只给 service role 读写。
- **面板不写库存**，只写"我按了采纳"。真正扣减仍是用户在手机上确认后的 `complete_meal`。

### 6.3 帧格式（省掉整块固件复杂度）

```
header: "FD3" + version + 3 帧数 + 每帧 9472 B（2bpp，GxEPD2 缓冲序）
总长: 8 + 3 × 9472 = 28424 B
```

设备拿到后写进 SPIFFS，之后 30 分钟轮播完全不联网；只有 6 小时一次的 ETag 检查需要 Wi-Fi。
即使 Wi-Fi 断了，冰箱门上那张画面照常轮播。

### 6.4 谁渲染这几帧

**渲染在 Node 里做，不在固件里做**：

- `tools/panel-render.mjs`：`require` 现有 `logic.js` + `data.js`（`globalThis.window = {}` 一下就能在 Node 里跑），算出三屏内容；
- 用仓库里自带的一张 **16×16 中文点阵字模表**（Python 脚本从 TTF 生成一次，约 200 字，60 KB）往像素缓冲上写字——不装 canvas、不装字体、CI 上不会因为缺中文字体挂掉；
- 打包成上面的 2bpp 格式，上传 Storage；
- GitHub Actions 每 30 分钟跑一次（免费额度够；也可以只在数据变动时由手机端触发一次）。

好处：**改版只改 Web，不重烧固件**；面板是彻底的哑终端。
代价：布局要在 Node 里再实现一遍（和 `display.html` 的视觉保持一致，用一个"对照页"并排看）。

### 6.5 四条铁律（沿用，不改）

1. 只有 `confirm_purchase` / `complete_meal` 改 `qty`。
2. 开始做饭只动 `reserved_qty`。
3. 拍照、识别、看菜谱，一次都不改库存。
4. 幂等靠 `rpc_calls.key` + 状态迁移，不靠前端置灰。

## 11. 三条不承诺（写进报告，别写进 PPT 的卖点）
