## 一、架构现状（已经落地，不是计划）

```
手机 PWA（登录态 JWT）
   │  读：GET items（RLS 只返回本家）
   │  写：RPC（SECURITY DEFINER，带幂等 key）
   ▼
Supabase
   ├ Auth（邮箱 magic link / 密码）
   ├ Postgres（households / household_members / items / inventory_events /
   │           meal_sessions / capture_* / receipts / devices / rpc_calls）
   └ RLS：本家可见，写一律走函数
```

**四条硬规则**（代码与数据库都按这个来）

1. 只有两件事会改 `qty`：`confirm_purchase`（确认采购）、`complete_meal`（完成烹饪）。
2. 开始烹饪只动 `reserved_qty`；取消只释放预留。
3. 拍照、识别、打开/选择菜谱：一次都不改库存。
4. 幂等靠 `rpc_calls.key` 唯一 + 状态迁移带 `WHERE status=…`，**不靠前端把按钮置灰**。

## 二、已验证（真实 API / 真实浏览器）

| 场景 | 结果 |
|---|---|
| 匿名读 `items` | **0 行**（RLS 生效前是 302） |
| 匿名调 `confirm_purchase` | `401 permission denied` |
| 登录用户读 `items` | 只返回自己家 |
| confirm_purchase ×2（同 key） | 只写一次，第二次 `duplicate:true` |
| reserve_meal | `qty` 不变，`reserved_qty` +1 |
| reserve_meal ×2 | `already:true`，不重复占用 |
| complete_meal | `qty` −1，`reserved_qty` 归零 |
| complete_meal ×2 | `duplicate:true`，`qty` 不动 |
| 取消 | `qty` 不变，预留清零 |
| 前端做饭（登录态） | `start_meal_session → reserve_meal → complete_meal → undo_event` 全通 |
| 前端采购（登录态） | `start_capture_session → save_capture_candidates → confirm_purchase` |
| 未登录路径 | 与改版前完全一致（本地存储），回归通过 |

## 六、代码约定

- 新页面复用 `ds.css` 的 token，不新开色板。
- 库存写入只走 RPC；在客户端拼 SQL 或直接 PATCH `items` 一律 review 不过。
- 每个 RPC 调用都要带 key（`<session>:<action>`），否则幂等失效。
- 失败要能重试：改动先进 outbox，联网后补推（`cloud.js`）。
