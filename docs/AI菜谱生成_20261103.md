# AI 菜谱生成（今天的锅）· 第一阶段

本机演示版：复用已有的 Ollama + 识别服务，给「今天的锅」加一条「库里没有就用 AI 现配」的路。
不新增模型、不改 Supabase、不往菜谱库写任何东西。

## 1. 现有环境（实测）

| 项 | 实际值 |
|---|---|
| Ollama | `http://127.0.0.1:11434`，只装了一个模型：`qwen2.5vl:3b`（3.8B，Q4_K_M，128k ctx，completion + vision） |
| 服务代码 | `C:\Users\22390\Desktop\fridge-ai-test\server.py`（Python 标准库 `http.server`，不是 FastAPI） |
| 调用方式 | `requests.post(f"{OLLAMA}/api/chat", json=body)`，**不用** Python ollama SDK，也不直连前端到 11434 |
| 约束参数 | `format` = JSON Schema，`temperature:0`（生成用 0.2）、`seed:0/7`、`num_ctx:8192`、`stream:false`、超时 300s |
| 提示词 / 返回格式 | 识别：`server.py` 的 `PROMPT` + `SCHEMA`；生成：`RECIPE_PROMPT` + `RECIPE_SCHEMA` |
| 启动 | `python start.py` → 起 `server.py --port 8941` + 静态站 8899 + cloudflared 隧道，打印 `?ai=` 链接和二维码 |

结论：**可以直接复用 `qwen2.5vl:3b` 和这一个服务**，不需要第二个文本模型，也不动库存识别那条链路。

## 2. 模型生成测试

同一模型、同一服务，`POST /api/generate-recipe`，上限 30 分钟：

| 用例 | 用时 | 菜名 | 必须食材进 ingredients | 必须食材进 steps | 结论 |
|---|---|---|---|---|---|
| 豆腐 + 鸡蛋 | 3.2s | 豆腐炒鸡蛋 | ✅ 豆腐、鸡蛋 | ✅ | 可用 |
| 豆腐 + 鸡蛋 + 番茄 | 4.3s | 豆腐番茄炒蛋 | ✅ 三样 | ✅ | 可用 |
| 豆腐 + 鸡蛋 + 青椒 | 4.0s | 豆腐炒青椒 | ✅ 三样 | ✅ | 可用（菜名漏了鸡蛋） |
| 紫薯 + 虾（库里 0 道） | 5.8s | 紫薯虾仁炒饭 | ✅ 紫薯、虾 | ✅ | 可用 |

- 步骤 4–7 步，写了火候和时间；`cooking_time` 给的是 25–30，不是照抄上限。
- 已知小毛病：菜名有时只写两样主料（青椒那道漏了鸡蛋）；偶尔把可选食材也堆进去。
- 不合格（必须食材没进 steps）时，服务端会带着修正提示**重试一次**，并把 `checks.must_use` 一起返回。

## 3. 接口

### `POST /api/generate-recipe`（别名 `/generate-recipe`）

请求：

```json
{ "must_use": ["豆腐", "鸡蛋"], "available": ["番茄", "青菜"], "max_minutes": 30, "avoid": ["豆腐炒鸡蛋"] }
```

- `must_use`：1–6 个字符串（前端传中文常用名）
- `available`：可选，最多取前 20 个
- `avoid`：可选，最多 6 个菜名；命中会带「换一道不同的」提示重试（L0 的「再配一道」靠它）
- `max_minutes`：5–120，越界会被夹到区间内
- 每次请求用随机 seed，所以同一组食材不会永远返回同一道菜

响应 200：

```json
{
  "ok": true,
  "reason": "ok",
  "recipe": {
    "name": "豆腐炒鸡蛋",
    "ingredients": [{ "name": "嫩豆腐", "amount": "300 克" }],
    "steps": ["…"],
    "cooking_time": 25,
    "extra_ingredients": ["葱姜蒜"],
    "warnings": ["豆腐先焯水去豆腥"]
  },
  "checks": { "must_use": { "豆腐": { "in_ingredients": true, "in_steps": true } }, "all_used": true },
  "meta": { "model": "qwen2.5vl:3b", "seconds": 3.2, "attempts": 1, "source": "ai", "must_use": ["豆腐", "鸡蛋"] }
}
```

错误：`400` 输入不合法（如 `must_use` 为空）；`502` Ollama 出错；`504` 模型超时。
`ok:false` 且仍带 `recipe` 时，说明两次都没满足「必须食材进 steps」，前端会带警示展示。

### `POST /api/recognize-ingredients`（别名 `/recognize`）

原有识别接口，参数和返回没变。

字段校验、超时（120s）、重试都只在服务端做；**服务不连 Supabase，也没有任何写库代码**。

## 5. 收藏（L1）

- 统一存 `localStorage['fd.favorites.v1']`：库里菜存 id，AI 菜整份存（没有 id）。
- 入口三处：菜谱卡右上角书签、菜谱详情底部「收藏」、AI 结果卡「收藏这一道」。
- 查看：菜谱页分类行最前面的「收藏 N」——不是新页面、不占新 tab，和类别筛选同一套机制。
- AI 收藏卡是虚线 + `AI 生成` 角标；点开能看食材、步骤、还要买、注意事项，也能「移出收藏」。
- 去重：同一来源同一道菜只存一条，重复点显示「已收藏」，不会再出现两条一样的。
- 跨设备不同步（二期再考虑 Supabase 表）。

## 5.5 前端怎么接

在 `cook.js` 里（页面 `cook.html` = 今天的锅）：

1. 先用原有逻辑从 373 道菜里检索（`FD.decide`），完全不动；
2. 算一下「库里同时用上锅里全部食材」的菜有几道（`dbAllUsedCount`）；
3. 0 道 → 结果下方出现醒目的 AI 卡（虚线边 + `AI 生成` 徽标）；有 → 只留一行「也可以用这几样让 AI 配一道 →」；
4. 点按钮 → `POST /api/generate-recipe` → 渲染 AI 卡：菜名、耗时、用到的食材、用量、步骤、还要买什么、注意事项；
5. 卡上两个动作：**收藏**（写 `localStorage['fd.favorites.v1']`，菜谱页的「收藏」里能看到）、**再配一道**（带 `avoid` 重新生成，不会给同一道）；
6. 失败有独立错误卡（连不上 / 超时 / 模型不合格），带「重试」。

服务地址沿用 `add.js` 的约定，不需要第二套配置：

```
?ai=<地址>  → 记进 localStorage['fd.ai.url']
http 页面   → 默认 http://当前主机:8941
https 页面  → 必须带 ?ai=，否则只提示、不发请求
```

## 6. 怎么打开（实测过）

| 场景 | 地址 | 结果 |
|---|---|---|
| 本机 + 本地站 | `http://127.0.0.1:8899/cook.html` | ✅ 自动直连 8941 |
| **本机 + GitHub Pages** | `https://jellyfishhamburger.github.io/fridge-decision/cook.html?ai=http%3A%2F%2F127.0.0.1%3A8941` | ✅ 实测调通（Chrome 把 loopback 当可信源，https → http://127.0.0.1 不算混合内容） |
| 手机 + 局域网 | `http://<电脑IP>:8899/cook.html` | ✅ 同一 Wi-Fi + 防火墙放行 8941 |
| 手机 + 线上页 | `https://…/cook.html?ai=<cloudflared 隧道>` | ✅ 需要 `start.py` 开隧道；隧道每次重启都变 |

打不开时的提示：页面会直接写「这一步需要本机 AI 服务…」，不会给一个点了没反应的按钮。

## 7. 还没解决的部署限制

- 手机打不开 `127.0.0.1`（那是手机自己）：要么局域网 IP（http），要么隧道（https）。
- 隧道地址每次重启都变；手机端要重新扫一次。
- 手机走局域网时，Windows 防火墙要放行 8941（和识别服务同一条规则）。
- 其他用户仍然用不了：这是本机演示，不是云端 AI。
- 模型输出是中文；英文界面下会多一行说明「模型用中文作答」。
- 收藏只存在浏览器本地，换设备/清缓存就没了；没有同步到 Supabase（这是有意的）。
- `server.py` 和 `start.py` 在 `C:\Users\22390\Desktop\fridge-ai-test\`，不在这个仓库里（沿用原有识别服务的位置）。
