# 稳定性修复 + 雪糕/饮料（2026-11-05）

## A. 自动检测录入为什么卡死

在 4× CPU 降速的 headless Chrome + 假摄像头下复现，对比同一份节点代码：

| 场景 | 旧版 | 新版 |
|---|---|---|
| `/health` 正常、`/recognize` 永不返回（隧道半死） | 6 次抓拍只成功 **1 张**，第 1 次 `snapOne` 卡 15.3s，最长主线程任务 **35.4s**，整页「网页暂无响应」 | 6 次抓拍全部成功（20–106ms/次），6 行都进入「没认出来 + 重试」，最长任务 **3.6s**（一次性模型加载） |
| AI 正常 | — | 10 张全部识别，抓拍 23–66ms，堆内存 12MB |
| 失败行 | 空行（`已拍 2 件 / 1 行`，照片与行对不上） | 每张一行，缩略图 + 重试，不丢照片 |

根因（都有代码证据）：

1. **`setInterval(tick, 220)` + 同步推理**：MediaPipe `detectForVideo` 在主线程跑，实测单帧 85–120ms（4× 降速），低端机会更久；定时器不等上一次结束，回调排队 → 主线程永不空闲。
2. **`snapOne` 里 `await classifySmart`**：拍一张就占住整条链路，AI 请求没有超时 → 第二张永远拍不上，`det.busy` 卡死。
3. **CLIP 兜底没有超时**：它从 HuggingFace 拉权重 + onnx wasm 编译，一次能把主线程锁 **34s**。`withTimeout` 在这种同步阻塞里根本轮不到执行。
4. **`go()` 不停止检测计时器**：离开拍摄页只 `stopCam()`，`det.running` 与 interval 还在，之后每 220ms 对着一块死视频调推理。
5. **未知行按 `cat === ""` 合并**：多张没认出来的照片并成一行，只留第一张图。

改动：

- 自适应节拍：`setTimeout` 自调度，间隔 = `clamp(detCost × 2.4, 160, 1000)`，至少留 55% 空闲。
- 识别与抓拍解耦：抓拍只做「截帧 → 缩略图 → 建行 → 入队」，识别串行队列后台跑，超时 9s + 单次重试，失败即把 AI 判为不可用（本轮后续走端侧）。
- CLIP 默认关闭（`?clip=1` 才开），并保留 3.5s 超时。
- 列表/条带只用 192px 缩略图，480 原图识别完立刻置空；取消/离开页面释放全部引用。
- 连续 5 次推理异常自动停止并提示；页面切后台暂停；`pagehide` 清理。
- 性能日志 `window.__fdPerf`（`?perf=1` 打到控制台）：记录尺寸、字节数、各阶段耗时、错误信息；不记录图片内容。

验收对照：10 张连拍 ✅、失败可恢复/重试 ✅、不重复提交（`state.locked` + 队列单飞）✅、取消释放 ✅、低端机（4× 降速）✅。

## B. 雪糕 / 饮料

- `data.js`：新增 4 个 `tag:"ice"`（雪糕/冰棍/冰淇淋杯/冰淇淋桶）+ 5 个 `tag:"drink"`（汽水/茶饮/果汁/咖啡/气泡水），共 118 种。
- `index.html`：新增两个分组（雪糕 / 冰品、饮料）与层位（冷冻、门架）；行内快速 ± 一件；行下显示品牌 · 口味 · 规格 · 已开封 · 位置。
- 编辑弹层新增「品牌 / 口味 / 规格 / 存放位置 / 已开封」，全部可选；老数据没有这些键，读出来是空。
- `logic.js`：`mergeItems` 的合并键加入品牌/口味/规格/位置/开封（老数据键为空，行为不变）；`FD.categoryStats(items)` 返回固定形状的计数（total / 各分类 / soon / expired），给墨水屏用。
- `receipt.js`：小票与 AI 名称映射补上雪糕/饮料的口语别名（可爱多、快乐水、东方树叶、元气森林…）。
- `cook-icons-extra.js`：9 个新食材各自的线条图标。

已知边界：牛奶仍归在「乳品」（老数据与菜谱都在用 `milk`，不重复建类）；云端 `confirm_purchase` 的 payload 没有扩展，品牌等字段只在本地版生效。
