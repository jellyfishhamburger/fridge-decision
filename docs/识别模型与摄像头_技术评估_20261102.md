## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 最推荐模型 | **Qwen2.5-VL-3B-Instruct**（Apache 2.0），本地 GGUF 推理，直接输出结构化 JSON |
| 辅助模型 | **Grounding DINO**（Apache 2.0）做「有哪几样 + 在哪 + 置信度」，VLM 只处理疑难样本 |

## 1. 现在的基线：9 类模型为什么到顶了

| 项目 | 现状 |
|---|---|
| 类别数 | 9 类（番茄、鸡蛋、牛奶、青菜、猪肉、豆腐、蘑菇、酸奶、面包一类） |
| 训练数据 | 少量合成 + 增强；真实照片只有 16 张做验证 |
| 真实准确率 | **约 50%**，食材类 7/10 |
| 输入 | 摄像头单帧 → 端侧 TFLite |
| 输出 | 类别 + 置信度，无位置、无数量、无「不确定」 |

三个结构性瓶颈，不是调参能解决的：

1. **封闭类别**。9 类之外一律不认识。要覆盖「几乎所有种类」，训练集至少上千类、每类上千张，这是数据工程不是模型工程。
2. **单目标假设**。分类器对整张图给一个标签，冰箱里同时出现七八样时它只能挑一个最像的。
3. **没有「不知道」**。softmax 永远给出一个答案，所以只能靠阈值猜；客户要的是「这我不确定，你确认一下」，这在分类器上做不出来。

**结论：这条路该停了，把力气放在开放词表的预训练模型上。**

## 2. 候选模型对比

### 2.1 逐项回答你的 6 个验证点

| 验证点 | Qwen2.5-VL-3B | Florence-2 (base/large) | Grounding DINO (Swin-T/B) |
|---|---|---|---|
| ① 未训练过的食材能认吗 | **能**（开放词表，靠语言知识） | 部分能（开放词表检测，但标签表达弱） | **能**（文本提示任写，如 "番茄, 鸡蛋, 豆腐"） |
| ② 一张图多种食材 | **能**，还能给数量 | 能，逐个区域 | **能**，逐框输出 |
| ③ 结构化 JSON + 置信度 | **能**，JSON 稳定；置信度靠自评（不可校准） | JSON 可拼，**但不输出置信度** | **能**，每个框带 score |
| ④ 本地跑 | 能（3B Q4 ≈ 2.2GB，CPU 也能跑，慢） | 能（0.23B，CPU 秒级） | 能（Swin-T ≈ 700MB，CPU 3–10s） |
| ⑤ 许可证 | **Apache 2.0** | **MIT** | **Apache 2.0** |
| ⑥ 对比 9 类模型 | 待实验，预计大幅领先（尤其漏识别） | 待实验 | 待实验 |

### 2.2 三个关键发现

**发现一：Florence-2 没有置信度。**
它是多任务通才（检测 / 字幕 / OCR / 区域描述），MIT 许可很友好，但**官方不输出 score**。你第 3 条明确要「置信度和不确定状态」，而我们整套产品逻辑是「低置信度不自动入库、必须用户确认」——用 Florence-2 就得自己另配一个打分器，等于多拼一个模型。**不建议做主模型，可做快速预筛。**

**发现二：YOLO-World 是 GPL-3.0。**
开放词表 + 实时 + 边缘友好，看起来很香，但 Ultralytics 系是 **GPL-3.0**：课程作业没问题，**一旦做成产品分发就要开源全部代码**。现在选它，等于给未来的商业化挖坑。同类里 **OWLv2（Apache 2.0）** 是更安全的零样本检测基线。

**发现三：Food-101 不能用。**
你提醒得对。Food-101 是 101 类**熟食菜品**（pizza、ramen、steak），拍的是摆盘成品，不是生鲜。拿它训「冰箱里的番茄/青菜」，域差极大。真正相关的公开数据是 **Fruits-360**（水果）、**Vegetable Image Dataset**、**VIREO Food-172**（中式菜）、**UEC-Food256**——但这些都还是「单主体、白底/摆拍」分布，跟冰箱俯拍的杂乱场景差距仍然大。**这也正是走零样本路线的原因：不去追数据集，让模型用语言知识直接认。**

### 2.3 还有哪些值得放进候选池

| 模型 | 体积 | 许可证 | 用途判断 |
|---|---|---|---|
| **Qwen2.5-VL-7B** | Q4 ≈ 4.7GB | Apache 2.0 | 3B 不够准时升级，同一套代码换权重 |
| **Qwen3-VL**（更新一代） | 视尺寸 | Apache 2.0 | 若 2026 年内稳定，直接替代 2.5 |
| **RAM++**（Recognize Anything） | ~1.5GB | Apache 2.0 | 纯打标签，适合「这堆是什么」预筛 |
| **OWLv2** | ~600MB | Apache 2.0 | Grounding DINO 的轻量替代 |
| **SAM 3 / SAM 2** | 视版本 | Apache/自定义 | 分割计数（「几个番茄」），非必需 |
| **CLIP / SigLIP** | ~350MB | MIT/Apache | 给检测框做二次命名，中文需多语版 |

## 3. 推荐技术路线：两段式，全本地

```
拍照 → 预处理（缩放/白平衡）→ ① Grounding DINO（词表提示，出框 + 置信度）
                                        ↓ 高置信直接收
                                        ↓ 低置信/未知物体
                                  ② Qwen2.5-VL-3B（看图 + 出 JSON）
                                        ↓
                              合并 → 待确认清单（现有流程不变）
```

**为什么两段而不是只用 VLM：**

| | 只用 Qwen2.5-VL-3B | 两段式 |
|---|---|---|
| 延迟 | 每张 15–60s（看硬件） | 常规张 3–8s，疑难才走 VLM |
| 置信度 | 自评，不可校准 | 检测器给真实 score |
| 数量/位置 | 文字描述，容易数错 | 框的数量直接可数 |
| 显存/内存 | 常驻 2.5–3GB | 检测器 700MB 常驻，VLM 按需加载 |

**输出 schema（建议固定，与现有待确认清单字段对齐）：**

```json
{
  "items": [
    {"name": "番茄", "name_en": "tomato", "category": "veg",
     "qty": 3, "unit": "个", "confidence": 0.82, "uncertain": false,
     "bbox": [120, 340, 260, 460], "source": "detector"}
  ],
  "unknown_regions": [
    {"bbox": [10, 20, 90, 120], "reason": "低置信，无法判定", "confidence": 0.31}
  ]
}
```

`uncertain: true` 的项在界面上默认不勾选——这条和现有「低置信度不默认入库」的规则一致，不需要改流程。

## 4. 费用拆解（把四件事分开算）

| 费用类型 | 一次性 / 持续 | 金额 | 说明 |
|---|---|---|---|
| **模型授权** | 一次性 | **HK$0** | Apache 2.0 / MIT，商用免授权费，需保留版权声明 |
| **训练 / 微调** | 一次性 | **HK$0–3,000** | 零样本先用 0 元；若要微调，租一张 24GB 显卡约 HK$3–5/小时 × 10–20 小时 |
| **云端推理** | 持续 | **HK$0** | 我们要的就是这个 0；只要推理在本地 |
| **本地硬件** | 一次性 | **HK$1,700–2,800** | 见第 6 节 |
| **电费** | 持续 | **≈ HK$0.02/次** | Pi 5 满载 10W，单次 30s ≈ 0.08Wh |

**必须说清的一句**：本地推理不是「免费的」，是**把边际成本从「每次几毛钱 API」换成「一次性硬件 + 每天几瓦电」**。用得多才划算：每天 3 次 × 一年 ≈ 1,000 次，云端按 HK$0.3/次算就是 HK$300/年，两年就跟一台 Pi 5 打平；每天 20 次则三个月回本。

**相反地**，不要以为「训练一次 = 以后永久免费」——如果训练出来的模型仍然部署在云上跑，那还是每次都要付推理费。**免费的前提是部署位置在我们自己手里。**

## 5. 本地推理可行性（算力对表）

| 设备 | 内存 | Qwen2.5-VL-3B Q4 能跑吗 | 预计单张耗时 | 判断 |
|---|---|---|---|---|
| **Pi Zero 2 W** | 512MB | ❌ 放不下 | — | 只能当拍照终端 |
| **Pi 5 8GB（纯 CPU）** | 8GB | ✅ 勉强（占 5–6GB） | **40–90s** | 能验证，产品上偏慢 |
| **Pi 5 + AI HAT+ 2** | 8GB + HAT 8GB | ✅（Hailo 已支持 ≤6B 的 VLM） | **5–15s** | 体验可用，但见下方警告 |
| **现成笔记本 / 台式（同 Wi-Fi）** | 16GB+ | ✅ | **5–15s** | **先走这条，0 元验证** |
| **Pi 5 + 纯检测器（Grounding DINO）** | 8GB | ✅ | **3–8s** | 常规场景够用 |

**关于 AI HAT+ 2 的警告（必须知道）**：$130、40 TOPS INT4、8GB 独立内存，官方说能跑 ≤6B 的 LLM/VLM。但 Tom's Hardware 与 Jeff Geerling 的实测发现，**在部分受支持的模型上，纯 Pi 5 8GB 反而比 AI HAT+ 2 更快**——原因是 HAT 的功耗被限制在 **3W**。所以：

> **不要在验证准确率之前买 AI HAT+ 2。** 先用 Pi 5 纯 CPU 或笔记本跑出准确率；只有当「慢到不可接受」且「准确率达标」时才升级。

## 6. 摄像头对比

### 6.1 三个方案

| | A. ESP32-S3-CAM N16R8 + OV5640 | B. Pi Zero 2 W + Camera 3 | C. Pi 5 + Camera 3 Wide (+ AI HAT+ 2 可选) |
|---|---|---|---|
| 价格（HK$） | 120–150 | 350–470 | 1,400–1,700（+1,000 HAT） |
| 传感器 | OV5640 5MP 1/4" | IMX708 12MP 1/7.4"等效（7.4mm 对角） | IMX708 12MP |
| **水平视角** | **55°**（D 68° / V 42°） | 标准 66° / 广角 **102°** | 同左 |
| **对焦** | **固定对焦**（出厂对无穷远） | **PDAF 自动对焦**，5cm–∞（广角） | 同左 |
| 近拍能力 | ❌ 25–40cm 会糊 | ✅ 5cm 起 | ✅ 5cm 起 |
| 本地推理 | ❌ 无 | ❌ 512MB 放不下 | ✅ |
| 功耗 | 0.5–1.5W | 1–2W | 5–10W（+HAT 3W） |
| 尺寸 | 最小（可藏进顶盖） | 小 | 大，需散热孔与风扇 |
| 开发难度 | 中（自己写拍照/上传固件） | 中（libcamera + Python） | 中高（散热、供电、系统维护） |

### 6.2 视角实算（这是最容易被「500 万像素」骗的地方）

覆盖宽度 = 2 × 距离 × tan(水平视角/2)。参照**香港常见小型冰箱内腔：宽 52cm × 深 48cm × 高 110cm**。

| 镜头到该层距离 | OV5640（55°） | Cam3 标准（66°） | Cam3 广角（102°） |
|---|---|---|---|
| 25cm | 26×19cm | 32×19cm | 62×33cm |
| 30cm | 31×23cm | 39×22cm | 74×40cm |
| 40cm | 42×31cm | 52×30cm | **99×53cm** |
| 50cm | 52×38cm | 65×37cm | 123×66cm |
| 70cm | 73×54cm | 91×52cm | 173×93cm |
| 90cm | 94×69cm | 117×67cm | 222×119cm |

**要一屏横向拍满 52cm 的冰箱层板，镜头到那层至少要：**

- OV5640：**50cm**
- Cam3 标准：**40cm**
- Cam3 广角：**21cm**

而冰箱顶部装好后，**最上面一层通常只有 20–30cm 距离**。这意味着：

> **OV5640 在最近的层板上只能拍到 26–31cm 宽——不到冰箱宽度的一半。** 再加上它是固定对焦（对无穷远清晰），20–40cm 内基本是糊的。500 万像素在这个场景里完全用不上。
>
> 这不是「可以调」的问题，是光学限制：换镜头才能解决，而换镜头后它就不是那个 90 块的模组了。

### 6.3 一个更根本的问题：装在顶部，看不到里面

「磁吸在冰箱顶部」指的是**冰箱外壳顶部**。摄像头朝下，看到的是**台面**，不是冰箱内部。关上门之后它什么也拍不到。

所以「装在顶部」这个产品形态要成立，只有三种真实可行的解释：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **台面俯拍**（推荐） | 设备吸在冰箱顶，**买菜回来把东西摊在台面上拍** | 视角、光照、距离都好控制；不用改冰箱 | 用户要多一步「摊开」 |
| **门框内侧** | 摄像头装在冰箱门内侧上沿，朝里拍 | 天然俯视整个内腔 | 走线穿过门封条、低温结露、门开合格挡视线 |
| **手持手机**（现状） | 手机拍 | 0 成本、对焦最好 | 不是「硬件产品」 |

**建议**：课程项目里先把「台面俯拍」写死为使用场景（用户本来就要把菜放上台面），摄像头固定在顶盖边缘、向下 30–40cm 对着台面。这样视角需求从「110cm 高内腔」降到「一张 60×45cm 的台面」，OV5640 都勉强够，但**近拍对焦**仍然只有 Camera 3 合格。

## 7. 模型与硬件的分工（不能含糊）

```
┌──────────────┐   JPEG 800×600    ┌────────────────────┐
│  摄像头（采集）│ ────────────────→ │  计算单元（推理）    │
│  Camera 3 /   │   HTTP POST        │  Pi 5 或笔记本      │
│  ESP32-S3-CAM │                    │  Grounding DINO     │
└──────────────┘                    │  + Qwen2.5-VL-3B    │
        ↑ 触发拍摄                    └─────────┬──────────┘
        │                                      │ 只写「待确认清单」
   App / Supabase 任务                        ↓
                                     ┌────────────────────┐
                                     │ Supabase（唯一主库） │
                                     │ capture_sessions    │
                                     │ items（用户确认后）  │
                                     └────────────────────┘
```

四条铁律（沿用已定架构，不新增入口）：

1. **ESP32-S3 只负责拍 + 传**。绝不在 8MB PSRAM 上跑视觉模型。
2. **推理单元不写库存**，只写 `capture_sessions` 的候选清单。
3. **只有用户确认**才触发 `confirm_purchase` 改 `qty`——这条已经在跑，不动。
4. **设备凭证**用独立的 device token（Supabase Edge Function 校验），绝不下发 service key。

**能不能把摄像头和算力装进同一个顶盖？**

- **能，但顶盖会变成 12×9×5cm 左右、带散热孔、需要 5V/3A 供电的盒子**，外观接近一个小音箱，不是「薄薄一片磁吸贴」。
- Pi 5 满载 5–10W，封闭盒内必须留风道，否则夏天降频。
- **折中**：顶盖只放摄像头（Camera 3 + 一条 15cm FPC 或 ESP32），算力单元放在冰箱旁边的插座上（Pi 5 藏在高处或冰箱背面），两者走 Wi-Fi。外观最干净，代价是多一个电源插头。

## 8. 对照实验方案（还没跑，这是要跑的东西）

**样本**：`Desktop\training` 里 41 张真实照片（其中 16 张已有 9 类模型的 ground truth）。

**对照 5 组**：

| 组 | 模型 | 运行方式 |
|---|---|---|
| 基线 | 现有 9 类 TFLite | 已有结果（≈50%） |
| M1 | Qwen2.5-VL-3B-Instruct Q4 | Ollama / llama.cpp，CPU |
| M2 | Florence-2-base | transformers CPU，`<OPEN_VOCABULARY_DETECTION>` |
| M3 | Grounding DINO Swin-T | ONNX Runtime CPU，提示词 = 我们的食材词表 |
| M4 | （可选）OWLv2-base | ONNX Runtime CPU |

**指标**（每张照片人工标注 ground truth：出现哪些食材、各几个）：

1. 名称命中率（正确识别 / 实际出现）
2. 漏识别率（1 − 召回）
3. 错误新增率（识别到但实际没有 / 识别总数）
4. 重复识别率（同一食材被多次报告）
5. 多目标表现（≥4 样同时出现时的命中率）
6. 遮挡表现（被挡住 ≥50% 的食材能否给出「不确定」）
7. 单张推理时间（冷启 / 热启分开记）
8. 峰值内存

**步骤**：

```bash
# 1) 拉模型（一次性，约 2.2GB）
ollama pull qwen2.5vl:3b

# 2) 跑 41 张，输出 JSON
python eval_vlm.py --photos Desktop/training --out results/qwen3b.json

# 3) 与 ground truth 比对，出混淆矩阵
python score.py --pred results/qwen3b.json --truth labels.csv
```

**预计耗时**：脚本 1 小时，跑批 1–2 小时（CPU 慢），人工标注 1 小时。**合计 3–4 小时。**

**开跑前先说清**：本报告里所有「预计准确率」都来自公开 benchmark 与规格推算，**不是我们实测**。真正能写进 PPT 的数字只有跑完这一轮才算数。

## 9. 与现有系统怎么接（不改已有流程的前提下）

| 阶段 | 动作 | 影响面 |
|---|---|---|
| **P0（本周）** | 笔记本跑 Ollama + 41 张照片出准确率 | 只出数据，零改动 |
| **P1** | 若准确率 ≥75%：把 `capture.js` 里的识别调用抽成 `recognize(image) → candidates[]`，云端/本地两个实现共用同一份 schema | 只加一层接口，不动 UI 与确认流程 |

| **P4** | 硬件定型、外壳、供电 | 纯硬件 |

**保留不动的部分**：现有 9 类模型（作为兜底/对比基线）、采购整理四步流程、`confirm_purchase` 与 `complete_meal` 的唯一写入口、RLS、Realtime。

## 10. 成本与难度总表

## 11. 风险登记

| 风险 | 影响 | 缓解 |
